# EcoTyper 项目代码规范

用户于 2026-10-06 明确要求本项目使用线性、命令式、研究脚本式的代码风格（linear imperative research scripting）。本文件是后续新增和修改代码的工作要求；项目完成后再进行全面代码审阅及可发表整理。

优先使用最基础、最直接的命令，减少函数封装、抽象层、循环和防御性代码。代码从上到下自然执行，让用户能够逐行理解数据处理过程。整体风格更接近 Stata do-file 或传统研究代码，而不是工程化 Python、R 语言项目。优先保证“看得懂、改得动、步骤清楚”。

保持代码紧凑：简单函数调用、变量列表、列选择、merge、rename、read_excel 等尽量写在一行。不要为了格式美观拆开简单命令；只有单行明显过长、包含多层逻辑或影响理解时才换行。不要使用 Black/PEP 8 式的强制展开格式，不设机械行宽上限。紧凑不等于挤在一行：一个独立操作通常占一行，不用分号把读取、筛选、计算、保存等不同动作串在一起。

## 脚本组织

- 先给阅读入口，再按步骤展开。文件开头用两三行中文交代本脚本做什么、在哪个环境/目录运行、读什么和写什么。正文按实际分析顺序，用 `# Step1. 读入数据`、`# Step2. 筛选候选基因` 这样的短标题分段；复杂步骤才增加一层小标题，不把每个赋值都变成一个章节。
- 每段先说明意图，再放直接命令。中文注释优先解释“为什么做、处理什么、关键参数是什么意思、接下来怎么看结果”。普通语法不逐行翻译；不写长篇讲义、口号或机械的“初始化/执行/结束”套话。
- 参数靠近实际调用。将阈值、维数、种子、线程数、模块数及绘图尺寸写在对应步骤附近，让人能找到修改位置。注释区分工具默认、本项目约定和数据支持的选择；需要保持可比性的参数说明其影响，不暗示可随意调参。
- 保留可检查的中间对象。读入、筛选、匹配、拟合、作图和保存顺着展开，不把多步处理藏在嵌套表达式、长管道或自定义包装函数中。已有清楚的短管道可以保留，不强制换语法。对象名称表达内容或角色，沿用稳定名称，不为风格统一做无意义改名。
- 让关键结果能就地核对。新写分析在真正有用的节点使用 head()、dim()、table()、length()、对象摘要或 Python 对应操作；批处理用明确的 print()。不要打印整张大矩阵，不要每行追加检查。仅整理既有代码风格时，不为形式增加新的计算或输出。
- 中间结果及时保存，输入输出一眼可见。读取、保存命令贴近对应步骤，路径沿用项目数据/代码/图件分区。计算耗时对象明确标出检查点用途；说明矩阵行列、计数层、单位、排序。

## 必要结构与修改边界

- 保留算法必需的循环、逐模块处理、同版多格式导出、绘图库要求的回调，以及防止错配或数据损失的检查，并用简短注释解释用途。
- 不为消除少量重复引入类、通用 pipeline、配置管理器或隐式缓存；不复制无关安装命令、清空工作区、整段弃用代码和多个未决分析分支。
- 留白为阅读服务：不同分析动作之间留一个空行，同一步相关命令放在一起；复杂绘图调用按数据、布局、文字、图例等参数组换行，不把每个短参数展开成一行。
- 注释与实际代码一致。不把旧模板参数、预期结果、历史方法或未经验证状态写成当前事实；不知道就明确限制。修改已有代码保留方法、数据、参数和结果语义，不能借“整理”悄悄改变筛选或统计。
- 把用户经验整理成可复用资产时，优先保证“意图不漂移 + 人能维护”，再追求抽象、标准化和工程化。让原用户更难理解、修改和验证的整理，默认视为退化。

验收检查：用户能否顺着读完、找到关键参数、查看中间结果、确认输入输出；纯风格整理还应验证执行逻辑和结果没有变化。已有脚本不在当前任务中自动全面重写。必要的数据隔离、行列匹配、源文件保护和 SSH 单连接规则继续执行。
